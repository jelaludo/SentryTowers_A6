# References to rigged animation patterns

The 27 October 2026 K9/Cheetah pass is a first working example of this workflow. It separates what a reference demonstrates from timing and movement choices made for our mechanical rigs. It currently needs an animator to interpret the source. Automatic video-to-rig conversion is a future experiment.

## Working example

`source/motion-patterns/quadruped-patterns.json` records reference provenance, observations, six K9 gait schedules and two jump profiles. `tools/blender/quadruped_motion.py` evaluates the reusable trajectories. The K9 builder and `cheetah_motion.py` adapt those trajectories to their existing skeletons. `workshop/quadruped-motion-inspector.js` displays the exported contact windows and jump poses in both viewers.

The useful reusable unit is a **motion pattern with events and constraints**: which paw supports the animal, when it releases, how the body travels, which parts respond later, and how the performance ends. Bone rotations are generated by each rig adapter because proportions, joint axes and mechanical travel differ.

The follow-up `quadruped-playground/` demonstrates a composition layer above those patterns: seeded pursuit and avoidance select the existing clips, stride metadata synchronizes cadence with actual movement, and named release/touchdown events delimit added airborne jump travel. Source motions stay unchanged. Its controller and actual-rig tests check the combined behavior, including transitions, grounded feet, actor separation and hurdle clearance. This is an authored example of composing reference-informed patterns; automatic reference extraction and arbitrary-environment planning remain future work.

## 1. Assemble a reference packet

Give each source an identifier, URL or local path, creator, access date, medium and intended use. Keep original files unchanged. Record redistribution rights separately from permission to observe a source; a link and notes are often sufficient for the repository. Keep hashes for local files, and preserve earlier asset revisions in Git.

For video, record the source frame rate, any slow-motion factor, clip timestamps, view direction and scale clues. A side view reveals the main trajectory; a front or rear view resolves limb spacing and overlap. Retain preparation and recovery, not just the airborne instant. For an image strip, record pose order and mark timing as unknown. For research, record species, task, experimental conditions, figure/table and what was actually measured.

Our Motion Zoo sources are authored animation studies. We use their contact diagrams and key-pose order as animation guidance. We do not treat them as measured force, speed or joint-angle data. No website images, videos or rigs are embedded in these exports.

## 2. Annotate before solving the rig

Make a short observation sheet with:

- A consistent limb legend: FL/FR/HL/HR from the animal's perspective.
- Paw touchdown and liftoff events, support intervals and simultaneous groups.
- Body/hip/chest trajectory landmarks, orientation, and head target.
- Takeoff, apex, first contact, deepest compression and settled pose.
- Secondary motion delays for shoulders, pelvis, tail and equipment.
- Confidence and uncertainty: hidden paws, perspective, missing frames, unknown timing.

A still image cannot determine event duration. The current jump seconds, flight height, duty factors and stride lengths are original authored choices. They are explicitly separated from observed pose order in the pattern file. If later footage supplies better timing, replace those choices with annotated measurements and retain the source mapping.

## 3. Author a reusable pattern

Store locomotion contacts as normalized cycle phases and one-shot events in seconds, with explicit duration and loop behavior. Use per-limb stance duration when needed. Put root-motion distance, placement behavior and units alongside the pattern. Pair the timing with broad trajectory controls rather than one rig's joint angles.

The current implementation supports constant-speed stance compensation, named touchdown groups, two flight intervals, fixed world paw anchors around jumps, a parabolic torso flight, separate airborne paw paths and a delayed chest-to-hip landing response. `Run_Cycle` keeps its historical engine-facing name but now correctly implements a diagonal trot. Pace, canter, rotary gallop and double-suspension sprint are separate clips.

## 4. Adapt to the rig

The adapter maps semantic parts to bones and sockets, reads rest lengths and solves the limbs. Mechanical plates remain rigid; body compression comes from joints rather than scaling armor. Verify the direction of every hinge, the available spine articulation, toe clearance and antenna/tail space. Preserve engine-owned pivots and runtime placement conventions.

The Cheetah profile travels 1.2 m in `MOTION`; K9 Jump stays in place. A paw target is converted from its fixed world anchor into the current rig frame while it supports the body. That keeps planted feet from following the translating torso. Each profile has its own proportions, heights, pitch and recovery timing.

## 5. Validate the exported performance

Run `tools/blender/check_quadruped_motion.py` before export to find unreachable targets or geometry below the floor. The asset validators then check plain and decoded compressed GLBs, 120 Hz skin envelopes, loop seams, stance drift, limb lengths, naming, sockets and budgets. `validate-quadruped-patterns.mjs` independently checks the expected gait groups, fore-before-hind jump events, apex clearance, planted world anchors and delayed hip compression.

The baseline ledgers record prior commits, node/socket interfaces, triangle/draw counts and existing clip durations. The faster-gait follow-up compares to `baseline-2026-10-27-contact-study.json`: explicitly requested duration changes are paired with matching travel-speed changes and checked for identical stride distance; other durations stay fixed. Changed motion can therefore be reviewed without silently changing those contracts. Hash-linked browser reports validate the actual published files.

Numerical checks do not establish acting quality, anatomical correctness, self-collision-free blending, force balance or terrain behavior. Review at real speed and slow speed, from side/front/three-quarter views. Inspect the transition into and out of a clip in the consuming game before runtime acceptance.

## 6. Review and hand off

Expose the reference-derived events in the viewer: four contact tracks, a moving playhead, current sole-height readout and seven named jump poses. Render an original pose sheet from the rig. Ask the reviewer to assess silhouette, weight, timing and intent; retain the feedback in the Devlog. Hand off the commit, asset folders, manifest, source, validation evidence and any remaining limitations.

## Possible next steps

1. A small annotation tool for video frame stepping, paw-event marking and timestamp export into this pattern format.
2. A library of reviewed patterns tagged by species, action, speed, lead limb and rig requirements, with mirrored leads and transitions authored separately.
3. Optional video pose estimation as an annotation aid, with explicit review of occluded limbs and camera motion.
4. Blend/state-transition and terrain-contact tests in the consuming game; later, compare biomechanical data where physical fidelity is required.

Start with the annotation tool and two or three well-reviewed motions before broadening the automation. The present code is a reusable authoring prototype, not a complete reference-ingestion product.
